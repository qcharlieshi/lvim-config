# Cockpit architecture alternatives — Rust TUI vs nvim-native vs tmux toolkit

**Date:** 2026-08-28 · **Scope:** evaluate two alternatives to design v4 (tmux-as-toolkit + Python CLI + nvim views) · **Method:** Exa web search, repo READMEs; no code run.

## A. Rust TUI (ratatui) as the cockpit UI

**What exists**
- **ratatui** is mature: `TestBackend` + `insta` snapshot testing is the documented norm ([ratatui.rs/recipes/testing/snapshots](https://ratatui.rs/recipes/testing/snapshots/)); a PTY end-to-end harness recipe is being added ([ratatui-website#1201](https://github.com/ratatui/ratatui-website/pull/1201), [ratatui-testlib](https://github.com/raibid-labs/ratatui-testlib)); async is user-managed via tokio `select!` over crossterm `EventStream` ([tutorial](https://ratatui.rs/tutorials/counter-async-app/full-async-events/), [FAQ](https://ratatui.rs/faq/)). Widget libs: rat-widget (tables, split, tabbed, menubar, file dialog), rat-salsa event queue ([awesome-ratatui](https://github.com/ratatui/awesome-ratatui)).
- **Embedding agents inside the TUI**: [tui-term](https://deepwiki.com/a-kenji/tui-term) (vt100 → ratatui widget) + portable-pty. Real-world lesson from [orcatui](https://github.com/lhjnano/orcatui): sophisticated agent TUIs (opencode, Claude Code) go blank unless you also inject `TERM`, answer capability queries (OSC 10/11, DECRQM, DA, DCS), and buffer mode-2026 synchronized-output batches. That is multiplexer work, not dashboard work.
- **Driving tmux from Rust**: [libtmux-rs](https://github.com/libtmux/libtmux-rs) (alpha; async, typed, **control-mode** transport = one connection, push notifications, 8 ms vs 168 ms for 6 commands; ships `tmux-mcp` and a tmuxp-style `tmux-workspace`). [rmux](https://github.com/Helvesec/rmux) is a Rust reimplementation of ~90 tmux commands with a ratatui pane widget and Rust/Python/TS SDKs — a different multiplexer, not a tmux client.
- **Rust agent orchestrators**: [bosun](https://github.com/johnuopini/bosun) is the closest to what a cockpit TUI would be: ratatui sidebar + live embedded preview of the selected *tmux* session (portable-pty + vt100 + tui-term), control-mode notifications, status detection from pane captures, dedicated `tmux -L bosun` socket. [lonko](https://github.com/lnds/lonko): tmux-side dashboard, worktree create/destroy, permission answering. [tmuxcc](https://github.com/nyanko3141592/tmuxcc): pane-scraping dashboard. [Shin-sibainu/ccmux](https://github.com/Shin-sibainu/ccmux) and orcatui own their PTYs and *replace* tmux (orcatui: 20 agents @ 60 fps, own daemon, SSH remote, mobile WS).

**What it enables over tmux chrome**: sub-pane widgets (tables, sparklines, trees) in one screen; a real fleet table with sort/filter/search; live preview + focus-in-place (bosun); mouse; a single consistent keymap; pixel-level control of layout inside one pane.

**What it does worse**: persistence/remote unless it *also* runs on tmux (bosun-style) or grows its own daemon (orcatui-style); composability — lnav/delta/hunk/nvim only appear if embedded through a PTY widget, with the query-responder/mode-2026 tax above; agent-controllability — the meta-agent needs a second control surface (IPC/HTTP) because it cannot press keys in a TUI; testing is snapshot-based and slower to iterate than shell-driving a CLI.

**Effort**: dashboard-only pane that reads `agents/*.json` and drives tmux (bosun-lite): **2–4 weeks** to parity with `hwatch cockpit status --pretty` + `display-menu`. Full tmux replacement with embedded agent PTYs (orcatui/rmux class): **months**, plus you re-own every multiplexer bug tmux already fixed.

**Risks**: PTY-embedding fidelity (blank panes, key encoding — bosun needed DECCKM, bracketed paste, SGR 1006, modifyOtherKeys); libtmux-rs is alpha; a Rust binary is a second toolchain in a Python+Lua repo; the widget the user *sees* is not the surface the agent *drives*, so two code paths drift.

## B. Neovim as the whole cockpit (and dropping LazyVim)

**What exists in core (0.12, Mar 2026)**: `:detach`, `:detach!`, `:connect {addr}`, `--remote-ui` — the TUI can leave a headless server running and reattach, closing [neovim#5035](https://github.com/neovim/neovim/issues/5035) ("like screen/tmux") ([:help ui-lifecycle](https://neovim.io/doc/user/gui/), [remote](https://neovim.io/doc/user/remote/)). `vim.pack` built-in plugin manager; floating windows with `statusline` and movable across tabpages; `nvim_open_term()` on non-empty buffers; mode-2026 synchronized output in `:terminal`; `[Process exited]` as virtual text; experimental `ui2` (no Press-ENTER) and `nvim__exec_lua_fast` for remote clients ([news-0.12](https://neovim.io/doc/user/news-0.12/), [jdhao summary](https://jdhao.github.io/2026/04/02/nvim-v012-release/)).

**Agentic-IDE plugins (2026)**
- Multi-agent terminals in splits: [nvim-agent](https://github.com/shalekeen/nvim-agent) (per-agent split + session dir + bundled MCP so agents edit buffers and message each other; checked-in "workspaces" launching agent sets), [aiterm.nvim](https://github.com/eltoto1219/aiterm.nvim) (terminal-first sessions with identity pinned at spawn; persistence via **shpool**; leased worktrees via treehouse; lualine tabline), [agent-term.nvim](https://github.com/alsi-lawr/agent-term.nvim) (per-agent persistent terminal, float/panel, native hook install), [auto-agents](https://github.com/yongjohnlee80/auto-agents) (one right panel, 0–9 agent slots, diff queue, vendored claudecode.nvim WS bridge).
- Fleet + review: [hangar.nvim](https://github.com/yal212/hangar.nvim) — "lazygit for coding agents": headless `claude -p` runs in worktrees, live dashboard (status/cost/turns/files), transcript tail, `diffsplit` vs base, squash-merge/discard; pure Lua, zero deps. [agent-review.nvim](https://github.com/colewhitley/agent-review.nvim) — annotate lines/hunks in Diffview, serialize to JSON/Markdown, send to the agent's **tmux pane** in one keystroke (this is our steer loop, already built). [neph.nvim](https://github.com/roshbhatia/neph.nvim) — hunk-by-hunk LLM review, WIP. claudecode.nvim / opencode.nvim — single-agent bridges with diff accept/reject.
- nvim-as-multiplexer: [spywhere/tmux.nvim](https://github.com/spywhere/tmux.nvim) (panes/windows/status bar; sessions were blocked on server/client — now unblocked by `:detach`), [terminal_mate.nvim](https://github.com/beardnick/terminal_mate.nvim) (nvim-first terminal with tmux fallback). Community write-ups ([jonfk](https://www.jonfk.ca/blog/neovim-as-terminal-multiplexer/), [duy.dev flightdeck](https://blog.duy.dev/my-setup-for-agentic-native-engineering-workflow-with-terminal-environment/)) converge on: nvim terminals are fine for *light* multiplexing; heavy multi-agent setups keep tmux (worktree-per-session via a `wt` script, sesh/sessionizer) and bind one agent into nvim.

**What it enables**: one keymap and one picker system for everything; floating/statusline widgets far richer than tmux chrome; agents can edit buffers directly (MCP); views are buffers, so annotate/lineage/`]d` motions are native; `:detach`/`--remote-ui` now gives tmux-like reattach.

**What it does worse**: process hosting — `:terminal` jobs die with the nvim process unless wrapped in shpool/tmux (aiterm's own caveat); one nvim becomes the supervisor of N agents (crash = fleet down; `:detach` protects against UI loss, not server loss); no `pipe-pane`-style capture, `select-layout` presets, or per-pane hooks without writing them; heavy TUIs (lnav, Claude Code itself) inside `:terminal` inherit nvim's redraw path and key stealing; the meta-agent drives nvim only through the RPC bridge (fine — the bridge exists) but every "view" must be Lua rather than "run this tool in a pane".

**LazyVim vs kickstart vs scratch**: the 2026 consensus is unchanged — distros buy the extras system and tested plugin graphs; hand-rolled buys "knowing every line" and freedom of keymaps ([samuellawrentz](https://samuellawrentz.com/blog/lazyvim-neovim-distro-2026/): "migrating mid-career costs more than it saves"; [Safi/kickstart](https://abdulkadersafi.com/blog/my-neovim-setup-a-kickstart-config-i-actually-understand); [Averpil: lazy.nvim→vim.pack](https://fredrikaverpil.github.io/blog/2026/04/15/from-lazy.nvim-to-vim.pack/) — "took more effort than expected… wait and see"). The user's config is ~35 active plugins with deep custom UI (dashboard animation, perf monitoring, terminal sync, bridge); a kickstart/scratch rewrite is **1–2 weeks to parity plus months of polish**, and nothing in the cockpit requires it: the cockpit needs ~500 lines under `lua/lib/cockpit/`, which is distro-agnostic.

**Effort**: nvim-native cockpit views (status buffer, pickers, annotate operator, lineage): **1–2 weeks** — same Lua either way. Making nvim the *host* of agents (replacing tmux): **3–6 weeks** to re-create spawn/capture/persistence/layout, ending near hangar.nvim + aiterm.nvim, minus tmux's process durability.

## Comparison

| Criterion | tmux toolkit (v4) | Rust TUI | nvim-native (LazyVim kept) | nvim-native (from scratch) |
|---|---|---|---|---|
| Keyboard / vim workflow | Good: key tables = modes; Space-hold layer; nvim for documents | Good inside the TUI; a second keymap to learn | Best: one leader, one picker system, buffer motions | Same as left, after rebuild |
| Glanceability | Adequate: badges, status line, `hwatch status --pretty`; tables in a pane | Best: sub-pane tables, live preview, sort/filter | Very good: floating/statusline widgets, `status.lua` | Same |
| Persistence / remote | Free (detach, resurrect, ssh) | Only via tmux (bosun) or own daemon (orcatui) | `:detach`/`--remote-ui` for the UI; agent processes still die with nvim unless shpool/tmux | Same |
| Composability (lnav/delta/gh/hunk) | Native: each is a pane | Embedded PTY tax (vt100, queries, mode 2026) | `:terminal` panes work; heavy TUIs are second-class | Same |
| Agent-controllability | Native: every action is a CLI verb; hooks are shell | Needs a parallel IPC/HTTP surface | Via nvim RPC bridge (exists) — every view must be Lua | Same |
| Maintenance burden | Low: ~1 Python file + tmux config + ~500 LOC Lua | Medium–high: Rust crate, PTY fidelity, second toolchain | Medium: Lua grows into a plugin; process supervision is ours | High: rebuild + cockpit |
| Migration from current setup | None | None (additive pane) | Low (additive `lua/lib/cockpit/`) | High: 1–2 wk parity, keymap muscle-memory reset |

## Recommendation

**Hybrid, weighted toward the current design: keep the tmux toolkit as the substrate and process host, keep LazyVim, build the cockpit's rich views in nvim (borrowing agent-review.nvim and hangar.nvim patterns), and treat a Rust TUI as an optional *widget* (bosun-style dashboard pane over `agents/*.json` + control mode) only if `status --pretty` + `status.lua` prove insufficient.** Do not make nvim the agent host and do not restart the config.

The three facts that drive it:
1. **The meta-agent is a CLI client.** tmux + the `cockpit` CLI give the human and the agent the *same* surface; a Rust TUI needs a second one and nvim-hosting turns every view into Lua the agent must call through RPC. agent-review.nvim shows the community landed on the same split: annotate in nvim, deliver to a tmux pane.
2. **Process durability lives in tmux.** nvim 0.12's `:detach`/`--remote-ui` fixes the *UI* half of "nvim as tmux"; the *process* half is still "terminals die with nvim" (aiterm.nvim's own caveat, hence shpool). Embedding agents in a Rust TUI reintroduces multiplexer problems orcatui documents (blank panes, query responders, mode-2026 batching).
3. **The rewrite has no cockpit payoff.** Every nvim-side piece the cockpit needs (~500 LOC under `lua/lib/cockpit/`) is distro-agnostic. Dropping LazyVim is a 1–2 week parity rebuild and a keymap reset on a 35-plugin config for zero functional gain; the consensus posts agree mid-career migration costs more than it saves. Revisit only if LazyVim's abstraction is what actually blocks a cockpit view — none identified.

Follow-ups worth stealing into the spec: agent-review.nvim's annotation → JSON/Markdown → tmux-pane delivery (validate our `annotate`/`review send` shape against it); hangar.nvim's dashboard fields (status, cost, turns, files changed, elapsed) for `status --pretty`; bosun's control-mode + `@bosun_container_id` user-option pattern for surviving tmux restarts; libtmux-rs control-mode numbers as the argument for a push (`tmux -C`) listener if polling ever hurts.
